## Decision and available environment

Use **required-content injection plus immutable addressed resources**, retaining
the existing Worker and task-lock protocol. Develop the first live candidate in
a disposable Linux container with a pinned Codex package. Do not introduce a
second Agent runtime or a new HTTP/MCP resource service. Native Skill discovery
must be independently inventoried and controlled before this candidate can run
real Skill jobs; this decision is not a claim that discovery is already isolated.

## Executable checks without credentials

`goodteam_os.skill_runtime_readiness` adds an explicit offline sandbox check to
the existing help/version inspection. It has **no live/model mode**, accepts no
credential reference or arbitrary command, and never enables product dispatch.

```sh
PYTHONPATH=src python -m goodteam_os.skill_runtime_readiness \
  --output /private/tmp/goodteam-readiness-UNIQUE \
  --codex /absolute/path/to/trusted/codex \
  --sandbox-checks
```

The parent of `--output` must exist, and the output must be a new canonical
path. On macOS, use `/private/tmp`, not the `/tmp` symlink. Existing output is
never overwritten. Omit `--sandbox-checks` for help/version inspection only.

Exit 2 deliberately means **not live-ready**. Read `readiness.json` and the
individual mode reports; a wrapper that successfully captures them has not
passed Runtime conformance. All report statuses concern the named fixed helper,
not model behavior or production Worker execution.

The diagnostic creates fresh HOME/CODEX_HOME/XDG/TMPDIR directories and passes no
inherited credentials, proxy settings, Python startup code or personal config.
A fixed Python helper reads and attempts to append to generated source, package,
outside-root and control-state sentinels. It also contacts its own loopback
listener. The same helper runs first as an unsandboxed positive control, on only
these disposable files, then under two Codex sandbox configurations:

1. Legacy `sandbox_mode="read-only"`, matching the existing Worker policy.
2. A candidate named profile granting read access to fixture source, resources,
   helper and Python runtime, denying general-root/temp access, with network off.

Positive controls must return exact generated byte digests and the listener's
random response. Missing tools, incomplete output, timeout, missing files and
connection refusal remain unverified. Only observed permission errors establish
a denial; changed sentinel bytes override a claimed denial. The parent records
changes before restoring its sentinels. No user source is read or changed.

## Disposable Linux envelope

The offline container uses an existing pinned image with Python, the integrity-checked
Linux binary/resources, and only the two diagnostic modules. It has no real
repository, personal HOME, SSH agent, Docker socket, credential, published port
or production service mount. Package acquisition occurs before sandbox testing;
the running test container has network disabled and installs nothing.

Required creation policy:

```text
--network none
--read-only
--cap-drop ALL
--security-opt no-new-privileges=true
--user 65534:65534
--pids-limit 64 --memory 768m --cpus 1
--tmpfs /tmp:rw,nosuid,nodev,size=128m,mode=1777
read-only mounts: /runtime (pinned CLI), /offline (diagnostic code)
```

Run the same module with the image's Python as `-m goodteam_os.skill_runtime_readiness`, with
`PYTHONPATH=/offline`, `--codex /runtime/bin/codex`, `--output /tmp/evidence`, and
`--sandbox-checks`. Capture the stopped container's image ID, creation policy,
exit code and `/tmp/evidence` before removing only that owned container. Export
tmpfs evidence while the container is still running (for example, stream a tar
from its parent process after the diagnostic finishes); tmpfs content disappears
on stop. Export the expected regular report files only, never follow CLI-created
runtime symlinks when extracting evidence on the host.

### Follow-up: working outer filesystem envelope

A later fixed-helper experiment retained network-off, capability-drop,
no-new-privileges, resource limits and the normal-user/read-only execution
container. Its per-container seccomp profile derives from the official Moby
allowlist and adds only `clone`, `unshare`, `mount`, `umount`, `umount2` and
`pivot_root`, permitting the inner bubblewrap namespace setup. This is an
**experimental policy**, not an approved production configuration. No unconfined
mode, added host capability or daemon change was used. The evidence records the
source profile URL/hash, added rule and resulting policy hash.

The original named profile then failed on read-only temporary-directory setup;
a directory-layout variant also failed before its helper. A host-bind variant
allowed private sample reads despite host mode restrictions and was rejected.
These failures remain in the evidence; their causes are not guessed away.

The successful candidate puts **only generated fixtures** into a pinned image
as root-owned files, with private sample directories mode0700 and files mode0600.
It mounts only the pinned runtime and diagnostic modules. A fixed-helper
positive control uses the same image as UID0 with a writable disposable layer;
the restricted run uses UID65534, a read-only image and the actual legacy Codex
sandbox. The parent separately copies fixture bytes from both stopped
containers, observing positive writes and unchanged restricted-run bytes.

| Observed fixed-helper contract | Result |
| --- | --- |
| Exact source and package reads | Both passed |
| Private control/outside sample reads | Both denied with EACCES |
| Source/package/control/outside writes | All four denied; original bytes unchanged |
| Connection to working in-container loopback listener | Denied with EPERM |

All **nine scoped checks** passed. The selected image is
`sha256:1c53d92470f27e2292cc8dea129a5445fbd3c9e082c76ec43a3750b1fd8addf0`;
the unchanged diagnostic modules come from source `4e975e99`. The
[evidence record](runtime-readiness-evidence.json) contains construction inputs,
actual commands/results, positive controls, policy and image identities, and
before/after digests. Owned containers were removed; the small derived image and
non-secret reports are retained for review. An initial Dockerfile using an image
ID as a registry name failed to resolve; the successful build uses the recorded
official registry digest and its existing ARM64 image.

This establishes an outer filesystem candidate for further work. It does not
make legacy read-only deny general reads by itself: confinement here depends on
the image contents, root ownership and mount policy. Real source/control storage
must remain outside the Worker view. The candidate still needs native Skill
inventory, descendant-process/discovery checks, provider egress, enforceable
request/cost limits and real Worker integration. Network-off cannot carry model
requests. `strict_binding_supported` and `live_ready` remain false.

## Concrete Worker integration

| Existing code | Required change and acceptance |
| --- | --- |
| `skills/worker_requests.py` preflight | Retain job publication, scope, task snapshot, digest, pins and current revocation. Require a server-owned verified adapter; preserve rejection for all other entries. |
| `skills/content.py` | Use the existing immutable context reference. Convert private input to model-visible text using explicit fields; never serialize `original_job_input` wholesale. |
| `WorkerJobStore._worker_prompt` | Inject complete required bodies and a versioned optional catalog before each fresh context. Use mapped runtime-relative paths; omit Operator paths and private source roots. Reject complete-input overflow without truncation. |
| `_worker_env` / `_prepare_isolated_codex_home` | Use a separate Skill adapter path with an allowlisted environment and fresh config. Do not inherit `os.environ`, reuse auth symlinks, copy personal config, or expose provider credentials to generated shell commands. Keep ordinary legacy workers' behavior separate. |
| `_command_with_execution_policy` / `_run_cli_worker` | The strict adapter must not inherit legacy `--sandbox read-only` accidentally. Bind actual binary/image/config/model/session identities and use the verified restriction mechanism. Own, terminate and reap the entire process group; uncertain termination stays unknown/stopping. |
| Resource delivery | Materialize only the pinned bound package files in a protected runtime view, preserving relative layout and exact digests. Source/control storage is outside that view. Recheck revocation before launch and stop active contexts on revocation. Bytes already delivered cannot be recalled. |
| Report capture | Capture the final CLI event through parent-owned stdout. Validate successful turn completion and persist the report from the Operator; never require Worker write access to the control-state directory. |
| Execution detail projection/UI | Expose task/snapshot/context/version identity, separately observed stages, failure reason and report state. Keep bodies, credentials and physical private paths out of public state. Reads do not become chat messages. |

This is the implementation order inside the existing S5 issue. The production
authority remains closed while the actual isolation mechanism is unresolved.
No test-only authority or hand-written evidence JSON can authorize a live Worker.

## Request and cost limits

The existing live probe bounds CLI contexts (one or two) and wall time, **not**
provider requests or dollars. One context can create multiple requests, tool
turns and retries. Killing a process does not undo already accepted provider work.
Neither output byte limits nor a model context-window setting enforce cost.

The proposed first live batch is two fresh contexts, at most 120 seconds each,
no automatic context retry, at most 20 total provider requests, and at most
USD 1 total provider spend. **These numbers are a review proposal, not user
authorization, configured limits, or a guarantee from the current CLI.**

Before using that batch, require an approved existing provider/credential path
that can enforce the request and spend ceilings outside the Worker. Verify
account isolation, model allowlist, exhaustion rejection and request accounting
with nonbillable controls first. The admission mechanism must reserve an upper
bound before forwarding each request, account for retries and in-flight work,
and refuse requests whose bound or price is unknown. A dashboard alert or a
post-completion usage total does not meet this contract.

Do not build a new proxy service just to claim this is satisfied. If the approved
provider path lacks enforceable limits, keep live execution blocked and present
that concrete limitation. The user may choose a suitable limited credential path
or explicitly approve a different exposure; do not silently treat timeouts as a
spend cap. Current diagnostic calls have zero provider requests and zero spend.

## Sources and verification

The [official permissions documentation](https://learn.chatgpt.com/docs/permissions)
describes separate filesystem/network profiles and warns that legacy sandbox
configuration takes precedence. It also distinguishes sandboxed command traffic
from model, connector, browser and other service traffic. These are design
inputs; the installed binary's actual behavior remains the acceptance source.
The [official Skill documentation](https://learn.chatgpt.com/docs/build-skills)
lists multiple discovery roots and per-Skill disabling; those settings alone do
not prove a task-specific allowlist.

Verification tier: Tier 3 for diagnostic evidence classification and Tier 4 for
actual offline CLI boundaries. On 2026-09-22 the operator accepted complete local
validation in place of waiting for remote CI. The local run uses an isolated
Python 3.12.11 environment, Node20, fresh test HOME/state directories and the
same full backend, HTTP recovery, frontend build/unit/lint and browser commands.
This does not turn a cancelled remote gate into a successful GitHub check.
Native/container diagnostics remain separate, credential-free prerequisites.
The PR records exact commands, source identity, counts, failures and retained
artifacts; all paid and real-model acceptance remains NOT RUN.

The first full macOS run exposed concurrent first-open failures in the existing
Skill/task/reviewer lock paths: `O_CREAT|O_NOFOLLOW` sometimes returned ENOENT
while another caller created the same file. A shared anchored lock-file opener
now elects one creator with `O_EXCL` and opens an existing file without
`O_CREAT`. It preserves nonblocking, no-follow, singly-linked regular-file and
`flock` checks. It never replaces a lock or recreates a missing read-path lock.
The proposal, availability, content, Worker request/creation, package, task and
Reviewer retry paths all use it. Regression coverage includes actual concurrent
opens and cross-process handoff plus unsafe/disappearing-file rejection.
