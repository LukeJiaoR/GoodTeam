# Bounded Goal continuation (first vertical slice)

Implementation: #540. Product acceptance remains #439; this does not close the
real-model Goal acceptance epic or replace #411's real-task usability evidence.

## Use it

In an already prepared project's Work page, explicitly confirm a Goal with its
objective, acceptance criteria, scope constraints, and maximum work-unit count.
Read the provider-charge notice and affirm it before confirmation. Existing
ordinary tasks are never converted or granted continuation permission.

The local server checks authorized Goals in the background. It starts their work
through the same workflow entrypoint, Workers, project configuration, Team, Skill
capture, readiness checks and approval Gates used by ordinary tasks. A completed
run triggers a read-only Manager evidence assessment. Unmet original criteria
become the next bounded work unit automatically, with a dependency and rationale;
there is no extra per-unit Start button. Original criteria are all reassessed at
each completed run so later regressions can reopen work.

Every workflow Gate still requires its existing decision. Reaching the confirmed
work-unit count presents a version-bound decision to add exactly one unit, up to
the hard ceiling of ten. Approving it continues the same Goal. Scope expansion,
changed runtime/Team/project configuration, failed assessment or an uncertain
execution outcome stops continuation. Stop/cancel affects future continuation;
an already started workflow retains its own existing controls.

**Work units are not dollars or tokens.** This slice does not impose a monetary
or token budget. Each run and its Manager assessment can incur the configured
provider charges. It captures explicit acknowledgement rather than implying a
cost cap or granting new provider/account permissions.

## Authority and evidence

- SQLite stores confirmed Goal intent, dispatch decisions, version-bound actions,
  evidence assessments and an outbox. It is not a second workflow engine.
- StateStore remains the authoritative workflow fact source. Goal work IDs bind
  deterministic run IDs. Current run identity and exact input must match before
  a result can advance the Goal.
- Only QA/code-review artifacts registered on that completed run and located
  under its run artifact directory enter the bounded evidence packet. The packet
  contains a trailing 32,000-character excerpt per artifact (full artifact digest);
  omitted content must not be treated as evidence of success. References
  include the run ID, artifact key and content digest. Foreign paths, oversized
  evidence and unavailable evidence fail closed.
- Each Manager check names an original criterion and a current evidence reference
  with a literal quote. All original criteria must be addressed, including those
  previously met. The complete assessment is retained for inspection.
- These are evidence-grounded Manager judgments, not independent proof of actual
  product correctness. A quoted report can itself be incomplete or wrong. Real
  model quality and real engineering outcomes still need the #439 demonstration.
- Next executable task text is generated by the control plane from the original
  confirmed objective, original scope, unmet criteria and evidence references.
  Manager-generated prose cannot inject a new executable task or permission.
- Project/Team/runtime configuration fingerprints must match the confirmed
  snapshot for further dispatch. New scope requires a new explicit Goal contract.

Kanban uses existing LocalTaskStore cards with stable Goal/work references,
criteria, dependency, priority, rationale and evidence. Its JSON read/modify/write
paths are locked and atomically replaced; corrupt data is preserved and rejected.
An outbox replay repairs projection without duplicating cards. A stopped Goal does
not falsely mark its already running workflow canceled.

## Recovery and limits

Project Goal locks serialize ticks and Goal decisions across threads/processes.
The existing workflow lock still serializes ordinary starts and Goal starts.
A persisted dispatch claim with a matching current run is reconciled; a claim
without a provable run is blocked rather than replayed. This intentionally does
not promise exactly-once external side effects after arbitrary runtime crashes.

The server must remain running for automatic continuation. Restart scans only
persisted explicit Goals and pending projection records. Read-only page requests
do not run the scheduler or create a Goal database for legacy projects.

An interrupted/failed Goal is inspectable and can be stopped before a new explicit
Goal is confirmed. This first slice does not include automatic retry of unknown
Worker outcomes, arbitrary scope-editing Gates, a monetary budget engine, a new
workflow builder or deployment.

## Verification levels

- Persistence tests cover atomic completion/derivation, optimistic versions,
  idempotency, process races, corruption, budget decisions, cancellation and
  crash-safe Kanban projection.
- Continuation tests cover result-derived follow-on work, duplicate ticks,
  unknown/lost dispatch outcomes, scope/configuration changes and existing real
  workflow Gates with local synthetic Workers.
- The isolated HTTP fixture exercises the production server/background service,
  task confirmation, workflow Gates, actual local synthetic Worker results,
  Manager result validation and same-Goal continuation. It never calls a paid
  model. It requires a system Git executable satisfying the production trust
  check; unavailable prerequisites are reported as skips, not successes.
- UI business-behavior tests cover explicit confirmation, charge acknowledgement,
  stable idempotency keys and exact revision-bound actions. Browser smoke uses an
  isolated server and synthetic Goal receipts; it does not validate model quality.

For a real demonstration, use the same Work confirmation on an isolated prepared
repository with an already authorized real Team/runtime. Choose a small Goal with
observable acceptance checks, retain all Gates and inspect each run's evidence.
Record the final revision, every work/run identity, assessment citations, actual
changes and verification, human interventions and provider spend. A fake or
synthetic PASS is never substituted for this outstanding product demonstration.

### Background recovery and stopping

The background service checks an unfinished workflow transition through the same
nonblocking workflow lock used by dashboard recovery. A live holder is left
alone. An abandoned transition is marked interrupted and the Goal is visibly
blocked; unknown work is never replayed automatically.

If project configuration or its authorization snapshot can no longer be read,
an active Goal becomes blocked. Stop/Cancel still accepts the original project
key, Goal identity, revision and idempotency key directly against the Goal ledger.
A successful stop receipt remains successful if the optional session/card
projection cannot be refreshed (`projection_unavailable: true`). It does not
terminate a Worker that was already dispatched.

Normal server shutdown stops further scans and waits up to 30 seconds for an
in-flight Goal tick after closing the HTTP server. A timeout is an explicit
shutdown error, not a successful drain. Abrupt process loss or an overlong tick
still requires the existing fail-closed recovery; this is not a cancellation or
automatic replay mechanism for unknown Worker outcomes.
