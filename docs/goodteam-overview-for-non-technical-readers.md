# GoodTeam 项目说明（非技术版）

## 一句话介绍

GoodTeam 是一个本地运行的 AI 产品团队系统。它把一个产品想法拆成需求、设计、开发、测试、审核、发布和复盘等步骤，并让不同 AI 角色像一个小型互联网产品团队一样协作。

简单说：GoodTeam 不是一个单独的聊天机器人，而是一个“会组织工作的 AI 团队”。

## 它想解决什么问题

现在很多人使用 AI 写代码或写文档，但常见问题是：

- AI 很容易直接开始写代码，却没有先把需求说清楚。
- 做出来的东西可能能跑，但不一定符合原始目标。
- 人很难知道 AI 现在做到哪一步、卡在哪里、谁在负责。
- 测试、审核、发布证据经常散落在聊天记录里，过几天就难以追踪。
- 一个项目反复迭代时，AI 容易忘记之前的决定和经验。
- 如果只靠人盯着，每次都要重新解释背景，成本很高。

GoodTeam 的目标是把这些事情变成一条可追踪的工作流。

## GoodTeam 像什么

可以把 GoodTeam 想象成一个本地的 AI 产品办公室。

这个办公室里有不同角色：

- 产品经理：把想法变成清晰需求。
- 架构师：设计实现方案和边界。
- 计划负责人：把工作拆成任务。
- UI 设计：定义界面体验，并推动真正的前端界面交付。
- 工程师：写代码、修问题、实现功能。
- QA：做测试和验收。
- Code Review：检查质量、风险和是否符合需求。
- Release：整理发布说明、风险和回滚方案。
- 复盘角色：记录经验，方便下一次继续。

这些角色可以由 AI 工具执行，但 GoodTeam 负责组织流程、记录状态、保留证据，并在关键节点让人审批。

## 它怎么工作

GoodTeam 的工作通常从一个目标开始，例如：

“开发一个内容运营工作台。”

然后它会进入一条类似真实产品团队的流程：

1. 理解项目背景。
2. 写出可决策的产品需求。
3. 等人审批需求。
4. 写出架构方案。
5. 等人审批方案。
6. 拆分任务。
7. 生成 UI 规格，并推动真实 UI 交付。
8. 派发 AI worker 去实现代码。
9. 派发 QA worker 做测试。
10. 做代码审查和发布检查。
11. 等人批准发布。
12. 记录复盘和项目记忆。

每一步都会留下文件、状态和证据，方便人随时查看。

## 人在里面做什么

GoodTeam 不是完全无人驾驶。它更像“自动推进 + 人类把关”。

人主要负责：

- 给出目标。
- 审批关键决策。
- 在需求、架构、发布等节点说“通过、修改、拒绝”。
- 查看测试和交付证据。
- 决定是否继续迭代。

这样人不用盯着每一行代码，但仍然掌握方向和风险。

## 它能产出什么

GoodTeam 一次完整工作可能产出：

- 产品需求文档。
- 架构方案。
- 任务拆解。
- UI 规格和界面交付结果。
- 实际代码改动。
- 测试报告。
- 代码审查报告。
- 发布说明。
- 审批记录。
- worker 执行日志。
- 项目记忆和复盘。

这些内容都保存在本地项目和 GoodTeam 工作区里，而不是只留在聊天记录中。

## Dashboard 是做什么的

GoodTeam 有一个本地网页看板，用来查看项目状态。

在看板里可以看到：

- 当前项目跑到哪一步。
- 哪些审批已经通过。
- 哪些 worker 正在运行、是否卡住。
- 产出了哪些文档和证据。
- 本地任务看板。
- smoke 测试记录。
- blocker 和风险。

这个看板的意义是让人不用猜 AI 做到哪里，而是直接看到工作流状态。

## Telegram 是做什么的

GoodTeam 可以通过 Telegram 通知人类审批。

当前 Telegram 已经能在进入审批门时主动发消息，并提供按钮让人批准、请求修改或拒绝。

但这个能力还需要升级。理想状态下，Telegram 消息不应该只是“有个审批”，而应该像一张手机上的 review 卡片：

- 这个项目是谁。
- 正在审哪个 gate。
- 当前测试是否通过。
- 是否有 UI 证据。
- 是否还有 blocker。
- 推荐去哪里打开完整 review 页面。
- 哪些按钮会真正改变 GoodTeam 状态。

也就是说，Telegram 应该是“提醒和快速决策入口”，完整审查仍然在 GoodTeam dashboard 中完成。

## GoodTeam 和普通 AI 编程工具有什么不同

普通 AI 编程工具更像一个工程师：你让它改代码，它就改代码。

GoodTeam 更像一个产品团队组织者：它不仅关心代码，还关心需求是否清楚、设计是否合理、测试是否真实、发布是否有证据、项目记忆是否能延续。

差别可以这样理解：

- 普通 AI 工具回答“我能写什么代码？”
- GoodTeam 回答“这个产品从想法到发布应该怎么被完整推进？”

## 为什么它强调本地优先

GoodTeam 的核心状态保存在本地：

- 项目配置。
- 当前 run 状态。
- 文档和产物。
- worker 结果。
- 审批记录。
- 本地任务和记忆。

这样做的好处是：

- 不依赖外部项目管理系统也能工作。
- 数据和项目上下文更容易留在自己机器上。
- Plane、Linear、GitHub Issues、Telegram 等外部工具只是可选同步和通知渠道。
- 即使外部系统不可用，本地工作流仍然可以继续。

## 现在已经做到什么

当前 GoodTeam 已经具备一条可运行的产品交付主线：

- 可以创建和管理项目。
- 可以从目标生成需求和架构文档。
- 可以在审批门暂停，等待人类决策。
- 可以派发 AI worker 做实现和 QA。
- 可以记录 worker 状态、日志、结果和卡住风险。
- 可以用本地 dashboard 查看项目、任务、worker、审批和产物。
- 可以通过 Telegram 发送审批通知。
- 可以运行 smoke loop 检查工作流是否还能跑通。
- 可以为目标项目执行本地测试、构建和验收。
- 可以让 UI 交付不再停留在文档，而是要求 worker 直接改出前端界面，并留下截图证据。

## 当前还需要改进什么

GoodTeam 还不是一个成熟的“全自动公司”。现在最需要改进的是 review 和审批体验。

主要问题包括：

- Telegram 消息还不够清楚，应该减少无用文件路径，增加结论和证据状态。
- Dashboard 的 `review` 页面还不是真正的专用审查工作台。
- 审批时需要更明确地展示“为什么可以批准”或“为什么不能批准”。
- Request changes 应该能带上具体修改意见，并驱动 GoodTeam 回到正确节点。
- UI 和产品体验还需要更强的验收标准，不能只看测试通过。

这些都是 GoodTeam 下一阶段要补强的地方。

## 一个简单例子

假设用户让 GoodTeam 开发一个叫 ContentOps Studio 的内容运营工具。

GoodTeam 不应该直接开始写代码，而应该先：

1. 理解这个工具给谁用。
2. 写出产品需求。
3. 让人审批需求。
4. 写出架构方案。
5. 让人审批方案。
6. 派 worker 实现产品。
7. 派 QA 验证它是否真的能把输入转成目标产出。
8. 展示测试、截图和证据。
9. 等人批准发布。
10. 记录这次做得好和不好的地方。

这就是 GoodTeam 的价值：它让 AI 开发更像一个可控、可审、可追踪的团队流程。

## 这个项目的最终愿景

GoodTeam 的长期目标是成为一个完整的 AI Native 产品团队操作系统。

它希望让一个人可以管理多个 AI worker，让它们围绕真实产品目标协作，而不是只完成零散任务。

理想状态下，用户只需要提出目标、把控关键决策、审查证据，GoodTeam 就能组织 AI 角色持续推进产品开发、测试、发布和复盘。

它不是为了取代人的判断，而是为了让人的判断用在更重要的位置。
