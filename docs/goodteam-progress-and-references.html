04 · Capability Map

已经形成的能力版图

项目与状态

  • 多项目 dashboard：概览与项目详情页。
  • projects/*.local.yaml 记录本机项目目标。
  • state/projects/<KEY>/current.json 记录活跃 run。
  • 删除操作限制在 GoodTeam 本地配置和状态，不删除目标 repo。

角色与模型

  • models.yaml 提供 balanced、cheap、max_quality。
  • 项目级 model_profile 与 role override 优先级已实现。
  • 核心角色路由已统一到 codex:gpt-5.5。

工作流门禁

  • PRD、RFC、delivery、release、retro 等审批节点。
  • blocked run 不能被误释放。
  • 支持 project-scoped retry，包括 staging-only retry。

Worker 与证据

  • Codex worker command 与本地环境对齐。
  • 非秘密 preflight 写入 status，便于诊断 auth/provider。
  • worker result、stdout、stderr 与 summary 作为后续 gate 的输入。

Smoke 与看板

  • goodteam_os.cli smoke 支持 dry-run、fake/noop/codex worker。
  • 报告写入 state/smoke-runs/latest.json。
  • goodteam_os.cli board 与 dashboard Agile Board 共用任务账本。

Staging 与交付契约

  • 当前 staging backend 支持 SSH + Docker Compose。
  • health、smoke、acceptance 分层记录步骤和证据等级。
  • delivery contract 让项目声明真正的功能验收，而不是由 GoodTeam 猜测业务。

07 · Next Moves

建议的下一步

1. 先收口当前分支

审批 AgentsMesh staging gate，若证据可接受，推进到 final release approval。这个动作会让 staging + delivery contract 的故事完整闭环。

2. 做真实 worker 毕业

用 worker-mode codex 跑一条端到端 smoke graduation，把 fake worker 之外的真实 Codex 调用纳入可引用证据。

3. 产品化证据面板

把 smoke report、staging report、acceptance checks、worker result、blocker task 聚合成 release readiness 页面。对标项目多在“能调度”，GoodTeam 的机会在“能判断是否可以交付”。

4. 明确对外定位

建议定位为“local-first AI product team runtime with evidence gates”，而不是另一个 coding agent dashboard。这样能避开 OpenHands/MetaGPT 的正面竞争，并突出 GoodTeam 已经做出的证据链。

5. 保留项目安全边界

继续坚持：项目配置不存 secret，删除只删 GoodTeam-local 状态，不删目标 repo；staging 执行记录命令元数据与结果，不复制密钥或托管远端主机。

6. 建立指标

新增每条 run 的 gate duration、worker retry count、acceptance failure type、release readiness score。这样 GoodTeam 后续可以从“工作流工具”进化为“研发运营系统”。
