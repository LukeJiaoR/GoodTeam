# GoodTeam UX / UI 整体梳理与三批改进

初次梳理：2026-09-21；第二批更新：2026-09-22。目标：操作顺畅、人机职责清楚、减少离开当前任务的跳转，形成从需求到交付的完整体验。

## 结论

GoodTeam 已有任务助手、当前任务提示、工作台内审批、变更讨论和交付报告。主要问题是这些能力还没有形成一致的任务上下文：工作台、评审、团队和知识库仍按功能分区；部分入口隐蔽，草稿与页面生命周期绑定，技术信息和需要用户决定的事情竞争注意力。

建议以“项目 → 当前任务 → 需要我做什么 → 结果”为信息主线。工作台承担日常闭环；配置、文档和审批详情可按需展开。保留独立页面给批量管理、深度编辑和直接链接使用。

本次保留现有技术栈与视觉语言，先修复连续操作。下面区分已落地、源码确认的问题、视觉观察和待验证假设，避免把方案当作已完成效果。

## 完整路径的梳理

| 阶段 | 现有体验与断点 | 目标体验 |
| --- | --- | --- |
| 选择项目 | 项目列表已有搜索、状态和导入；项目内切换主要需要回列表 | 项目名旁提供切换入口；回列表保留筛选和位置 |
| 表达需求 | 任务助手已有建议和变更模式；未发送输入原来只存在组件状态中 | 从任何详情返回都继续原草稿；明确发送、讨论、确认启动之间的区别 |
| 准备项目 | 项目模式、命令、约束、任务确认已经内联 | 一张准备清单呈现已完成、当前缺项、下一步；保留必要确认而减少重复说明 |
| 配置团队 | 从工作台的配置运行时链接进入团队页，再返回 | 常用配置在侧面板完成；完整团队管理仍可独立打开 |
| 执行 | 执行、助手、结果三栏并列；无任务也保留空列 | 尚未启动时突出输入；执行后逐步出现进度与结果；细节按需查看 |
| 人工决策 | 工作台已有原位审批；另有独立评审页和详情中的跳转入口 | 普通审批在同一任务里完成；编辑完整文档才进入深度视图，返回时恢复原位置 |
| 要求修改 | 独立评审页发起变更后会导航回 Work；工作台已有绑定目标的变更讨论 | 所有入口使用同一变更流程，持续显示修改目标、解释、待确认状态和最终结果 |
| 阅读资料 | 知识库内部切换原来覆盖查询参数；部分加载失败被吞掉 | 切换保留搜索条件；读取失败可在原位重试，不能看起来像“没有资料” |
| 完成交付 | 报告已经支持原位展开及历史身份绑定 | 首屏说明完成内容、验证范围、待办、下一步；技术证据放入次级详情 |
| 回看历史 | 历史选择器原来位于工作台导航的悬停浮层 | 显式“任务与历史”入口；历史只读、返回当前任务清楚可见 |

## 建议的信息架构

```text
项目切换 / 当前任务 / 状态与下一步
├─ 任务与历史（按需展开）
├─ 主工作区
│  ├─ 对话与需求
│  ├─ 当前待确认事项
│  └─ 输入与跟进
└─ 按需详情
   ├─ 进度和执行
   ├─ 结果、文档、审批
   └─ 团队与配置
```

这不是要求将全部信息堆到一个超长页面。默认只展示当前阶段需要的信息：输入需求时突出输入，执行时突出进展，需要决策时突出证据和决定，完成时突出交付。完整文档和批量管理保留深度视图。

## 三条关键交互闭环

1. **需求到启动**：输入需求 → 助手理解 → 可编辑任务摘要 → 缺项准备 → 明确确认 → 显示已启动及当前步骤。发送消息不等于批准执行。
2. **评审到修订**：收到待审提示 → 在当前任务展开证据 → 批准或提出修改 → 查看系统理解 → 确认修改 → 等待新证据。不能用自然语言讨论替代显式批准。
3. **交付到下一任务**：查看成果摘要 → 展开验证依据及局限 → 定位未完成事项 → 在同一工作台继续提问或创建下一任务。历史报告必须标明归属，历史浏览保持只读。

## 第一批实现的边界

- 仅修改前端呈现、浏览器会话草稿、知识页读取反馈及相关测试，不改变 API、账本、审批权限或 Worker 调度。
- 草稿使用 `sessionStorage`：同一标签页跨页面和刷新恢复；项目/run 分开。关闭标签页后不承诺恢复，不提供跨设备同步；存储不可用时仍可输入发送。
- 普通消息与变更讨论仍按原有输入模式分开。服务器上已保存的变更讨论仍以原有服务端状态为依据。
- 请求成功后才清除对应文本；请求进行中继续输入的新文本会保留；离开页面后请求完成也清除匹配的已发送草稿。
- 展开任务历史不再覆盖工作区，也不会因移开鼠标自行关闭。当前任务与下一步仍独立常显。
- 第一批没有移除独立评审页、没有实现配置侧面板，也没有完成三栏重排。减少主要业务跳转属于下一批。

## 第二批实现记录（2026-09-22）

本批直接处理日常操作的页面往返，落地 UX-05、UX-06 的常用路径和 UX-08，同时保留第一批草稿恢复等行为。

### 原位助手配置

- 工作台“配置运行时”打开右侧配置面板。保存和检查连接后留在面板，关闭回到原输入与按钮焦点。
- `WorkerDialog.jsx` 从 TeamPage 提取；两处共用同一表单。`saveAssistantRuntime.js` 共用原有“保存设置 → 显式只读模型检查 → 刷新状态”的流程。
- 保存检查继续呈现可能产生服务费用的说明，只有用户点击才调用。打开面板、切换字段不会发起模型调用或启动任务。
- 已验证或模拟模式的运行时详情默认收起；未验证、失败等状态保持可展开的检查入口。配置按钮始终可发现。
- 本批只内联助手运行时；增加/删除 Worker、职责组批量配置仍使用完整团队页。

### 原位完整评审

- 从工作台任务详情进入“查看与编辑评审文档”，打开文档/决策侧面板，URL 保持当前 run。
- 直接复用 ReviewPage、useReviewArtifactDraft 与原 API，保留完整文档读取、证据版本、冲突检测、保存后回读、人工决定等原有合同。
- 侧面板绑定打开时的 run；没有绑定或当前 run 变化时停止显示可操作评审，提示返回任务重新打开。选定审批缺失时不自动替换成另一个审批。
- 批准后主工作台刷新，但用户仍可查看本次结果；关闭回到当前任务。发起修改讨论后回到同一工作台输入框，已有普通消息草稿仍保留。
- 文档有未保存编辑时，关闭面板必须选择继续编辑或放弃。未保存文档不能直接跳到变更讨论，避免丢失编辑内容。
- 使用浏览器原生模态 dialog 隔离背景操作、处理 Esc 和焦点；侧面板按桌面两列、窄屏一列呈现。独立评审页继续提供评审队列和直接链接。

### 空闲工作台

- 当没有活动 run、执行成员、结果任务和交付报告时，仅显示居中的任务助手，减少空列。
- 有任务、执行或交付证据时保留原三栏，不因“暂无当前任务”而隐藏已有交付材料。
- 空闲移动端去掉无内容的执行/结果切换；对话草稿和任务助手始终保留。
- 活跃三栏在短视口下的进一步高度重排、交付报告归属说明、项目切换器仍属于后续范围。
